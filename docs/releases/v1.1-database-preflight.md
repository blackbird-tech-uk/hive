# HIVE V1.1 — production database preflight (read-only)

**Do not run against production without authorised database access.** These queries are read-only. Record results privately; do not paste connection strings, credentials, or personal data into issues or logs.

## Before the V1.1 migration

Run against the intended production PostgreSQL database, **before** migration `f31a6b8c02e4`:

```sql
-- Current Alembic revision; expected predecessor is 7c2a91d4e6f8.
SELECT version_num FROM alembic_version;

-- Number of organisations controls legacy-event backfill behaviour.
SELECT COUNT(*) AS organization_count FROM organizations;

-- Legacy events have no organization_id yet; count and sample ownership via approved business records.
SELECT COUNT(*) AS legacy_event_count FROM events;

-- Check for unexpected event-to-organisation relationships in application records
-- before adding the nullable ownership column.
```

## Important migration behaviour

- If **exactly one** organisation exists, the migration assigns all existing events to it.
- If **zero or multiple** organisations exist, legacy events remain unowned (`organization_id IS NULL`) and the new organisation-scoped endpoints cannot access them until ownership is resolved through an approved process.
- The migration adds `map_areas`, `events.organization_id`, and `assignments.map_area_id`.
- Downgrading drops the map areas and both added columns, causing data loss. **Do not use downgrade as the routine application rollback.**

## After migration, before promoting the API

```sql
SELECT version_num FROM alembic_version;
SELECT COUNT(*) AS unowned_events FROM events WHERE organization_id IS NULL;
SELECT COUNT(*) AS invalid_ownership
FROM events e
LEFT JOIN organizations o ON o.id = e.organization_id
WHERE e.organization_id IS NOT NULL AND o.id IS NULL;
```

If unowned events are present, stop and investigate; **never assign them to an arbitrary tenant**. Record the backup identifier, restore rehearsal, responsible operator, and rollout/rollback decision in the private release log.

## Staging requirement

Use a separate staging API and PostgreSQL database. Do not point a release preview at production for login, migration, create/update/delete, or assignment tests. Test with fictional events and test scanners only.
